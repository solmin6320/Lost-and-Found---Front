# 디자인 · UI/UX 품질 기준

이 프로젝트에서 **가장 우선하는 가치**다. 기능이 동작하는 것은 최소 조건이고, 여기 적힌 것을 만족해야 "끝났다"고 말한다.

`front-design-rules` 스킬이 **이 서비스의 구체적 규칙**(배지 체계, 결과 고지 문구 등)을 담는다면, 이 문서는 **모든 화면에 적용되는 품질 기준**이다. `frontend-design` 스킬(미감)과 함께 읽는다.

---

## 0. "끝났다"의 정의

화면 하나를 끝냈다고 말하려면 아래를 전부 만족해야 한다. 하나라도 빠지면 진행 중이다.

- [ ] 로딩 · 비어있음 · 오류 · 권한 **네 상태가 다 있다**
- [ ] 375px에서 가로 스크롤이 없다
- [ ] 키보드만으로 모든 동작이 가능하고, 포커스가 어디 있는지 보인다
- [ ] 되돌릴 수 없는 동작에 결과가 고지된다
- [ ] 제출 중 버튼이 잠긴다
- [ ] 느린 네트워크에서 레이아웃이 튀지 않는다
- [ ] 스크린샷 한 장으로 보여줄 수 있다

마지막 항목이 기준이다. **이 화면들은 포트폴리오에 실린다.** 기능만 되는 회색 화면은 목적을 절반만 달성한 것이다.

---

## 1. 첫인상 — 템플릿처럼 보이지 않는다

AI가 만든 화면에는 반복되는 기본값이 있다. 그게 보이면 "대충 만들었구나"로 읽힌다.

| 피할 것 | 대신 |
|---|---|
| 모든 모서리를 같은 반경으로 | 요소마다 다르게 — 썸네일 6 / 버튼 8 / 카드 12 / 배지 999 |
| 카드마다 그림자 | 1px 경계선. 그림자는 **실제로 떠 있는 것**(모달·시트)에만 |
| 보라 그라데이션, 크림+테라코타 | 이 서비스의 팔레트(`tokens.css`) |
| 폰트 두세 개 섞기 | Pretendard 하나. 굵기와 크기로 위계를 만든다 |
| 모든 곳에 색 | **색을 쓰는 곳은 유형 배지뿐.** 나머지는 잉크와 종이 |
| 아이콘 남발 | 텍스트로 충분하면 텍스트 |

**여백이 가장 싸고 효과적인 도구다.** 요소를 더 넣기 전에 간격부터 조정한다.

## 2. 가독성 — 한글은 영문과 다르다

- **`word-break: keep-all`** — 한글 단어가 중간에서 끊기면 읽는 속도가 눈에 띄게 떨어진다
- **행간 1.7** — 영문 권장치(1.5)보다 넉넉해야 한다. 한글은 글자가 빽빽하다
- **본문 16px 하한** — iOS Safari는 16px 미만 입력 필드에 자동 확대를 건다. 화면이 갑자기 튄다
- **한 줄 45~75자** — 넘으면 다음 줄 첫 글자를 찾기 어렵다. 본문 컨테이너에 `max-width`를 둔다
- **대비** — 본문 4.5:1, 큰 글씨 3:1 (WCAG AA). 눈대중 말고 계산한다
- **회색 글씨를 남발하지 않는다.** 보조 정보라고 다 흐리게 하면 화면 전체가 흐릿해진다

### 숫자와 날짜

- 날짜는 `2026. 9. 23.`처럼 **자리를 고정**한다. 목록에서 세로로 안 맞으면 스캔이 깨진다
- 상대 시간("3일 전")은 7일까지만. 그 뒤엔 절대 날짜가 낫다
- 조회수 같은 숫자는 `tabular-nums`로 폭을 고정한다

## 3. 사용자 우선 — 시스템이 아니라 사람 기준으로 쓴다

### 문구는 사용자의 말로

| 시스템 말투 | 사용자 말투 |
|---|---|
| "게시글이 존재하지 않습니다" | "삭제되었거나 없는 게시글이에요" |
| "유효하지 않은 요청" | "제목을 입력해 주세요" |
| "처리 중" | "사진 올리는 중… (2/5)" |

**오류 문구는 프론트가 짓지 않는다.** 백엔드 `ErrorCode`가 이미 한글 문장을 갖고 있다. 프론트가 직접 쓰는 건 **빈 상태 · 확인 다이얼로그 · 결과 고지 · 네트워크 끊김** 넷뿐이다.

### 막다른 길을 만들지 않는다

모든 오류 화면에는 **나갈 문**이 있어야 한다.

- 404 → "목록으로 돌아가기"
- 네트워크 오류 → "다시 시도"
- 403 → 왜 안 되는지 + 다음에 할 일

### 사용자가 한 일을 잃게 하지 않는다

- 폼 제출이 실패해도 **입력값을 지우지 않는다**
- 작성 중 이탈은 `beforeunload`로 확인
- 로그인이 필요해 튕겨냈다면, 로그인 후 **원래 가려던 곳으로** 돌려보낸다

---

## 4. 체감 속도 — 실제 속도보다 중요하다

| 대기 시간 | 사용자 인지 | 필요한 처리 |
|---|---|---|
| ~100ms | 즉시 | 없음 |
| ~300ms | 살짝 느림 | 버튼 눌린 상태 |
| ~1초 | 기다리는 중 | 스켈레톤 |
| 1초 이상 | 멈춘 것 같음 | 진행률 또는 단계 안내 |

- **스켈레톤 > 스피너.** 스피너는 "얼마나 걸릴지 모름"을 뜻하고, 스켈레톤은 **레이아웃을 미리 잡아** 화면이 튀지 않게 한다
- 이미지에는 `width`/`height` 또는 `aspect-ratio`를 지정한다. 없으면 로드될 때마다 아래 내용이 밀린다
- 이미지 업로드는 **몇 장 중 몇 장째인지** 보여준다. 5장이면 수 초가 걸린다
- 목록 이미지는 `loading="lazy"`

---

## 5. 일관성 — 같은 것은 같게

사용자는 규칙을 배운다. 규칙이 흔들리면 매번 다시 배워야 한다.

- 같은 동작은 **항상 같은 자리**. 목록 카드의 배지 위치가 화면마다 다르면 안 된다
- 주 동작 버튼은 항상 같은 스타일·같은 정렬
- 간격은 토큰에서만 가져온다. `margin: 13px` 같은 값이 나오면 토큰이 부족한 것이지 예외가 필요한 게 아니다
- 같은 데이터는 같은 형식으로. 목록의 날짜와 상세의 날짜가 다르면 안 된다

---

## 6. 모션 — 목적이 있을 때만

- **상태 변화를 설명할 때만** 쓴다. 장식용 애니메이션은 넣지 않는다
- 150~250ms. 길면 느리게 느껴진다
- `ease-out`(들어올 때) / `ease-in`(나갈 때)
- **레이아웃을 흔드는 애니메이션 금지.** `transform`과 `opacity`만 쓴다
- `prefers-reduced-motion: reduce`를 반드시 존중한다. 전정기관 질환이 있는 사용자에게는 어지럼증을 유발한다

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    transition-duration: 0.01ms !important;
  }
}
```

## 7. 접근성 — 최소선이 아니라 기본

- 모든 폼 입력에 `label` (`placeholder`는 label이 아니다 — 입력하면 사라진다)
- **색만으로 정보를 전달하지 않는다.** 배지는 색 + 텍스트, 오류는 색 + 아이콘 + 문장
- 포커스 링을 지우지 않는다. 디자인이 맘에 안 들면 다시 그리되 없애지 않는다
- 터치 대상 최소 44×44
- 이미지 `alt`는 "이미지"가 아니라 내용. 장식용이면 `alt=""`
- 본문 바로가기 링크(skip link)
- 동적으로 바뀌는 영역에 `aria-live` — 검색 결과 개수 같은 것

---

## 8. 모바일이 기준 — 데스크톱은 넓어진 모바일

사용자는 **물건을 잃어버린 직후, 길에서** 이 서비스를 연다.

- 한 손 조작. 주 동작 버튼은 **엄지가 닿는 아래쪽**에
- 밝은 야외 — 대비가 낮으면 아예 안 보인다
- 느린 네트워크 — 이미지가 무거우면 목록이 안 뜬다
- 입력 타입을 정확히 — `type="email"`, `inputMode="numeric"`. 키보드가 바뀐다
- 하단 고정 요소는 `env(safe-area-inset-bottom)`을 고려한다

---

## 9. 빈 상태를 설계한다

빈 화면은 **오류처럼 보인다.** 가장 자주 방치되고 가장 티가 나는 자리다.

| 상황 | 필요한 것 |
|---|---|
| 검색 결과 0건 | 왜 없는지 + 조건을 넓히는 방법 |
| 첫 방문(글이 없음) | 무엇을 할 수 있는지 + 첫 행동 버튼 |
| 내가 쓴 글 0건 | 권유. "아직 올린 글이 없어요" + 글쓰기 |
| 댓글 0건 | "첫 제보를 남겨보세요" |

---

## 10. 마이크로카피

- 버튼은 **동사**로. "확인"보다 "삭제하기", "등록하기"
- 다이얼로그 버튼은 **무슨 일이 일어나는지** 말한다. "예/아니오"보다 "삭제하기/취소"
- 부정문보다 긍정문. "취소하지 않으려면"보다 "계속 작성하려면"
- 사과하지 않는다. "죄송합니다"보다 **무엇을 하면 되는지**

## 11. 반응형 — 기기가 아니라 내용이 기준

### 브레이크포인트는 내용이 깨지는 지점에서 끊는다

"아이폰 12는 390px"처럼 기기 이름으로 정하지 않는다. 기기는 계속 나온다. **레이아웃이 어색해지는 폭**에서 끊는다.

| 토큰 | 폭 | 이 지점에서 바뀌는 것 |
|---|---|---|
| `--bp-sm` | 480px | 목록 2열, 필터가 한 줄에 들어감 |
| `--bp-md` | 768px | 사이드 여백 등장, 상세가 2단 |
| `--bp-lg` | 1024px | 목록 3열, 필터가 상단 고정 바 |
| `--bp-xl` | 1280px | 목록 4열, 본문 최대폭 도달 |

**모바일 우선으로 쓴다.** 기본 스타일이 좁은 화면이고 `min-width`로 넓혀간다. `max-width`로 깎아내려가면 예외가 겹쳐 금방 엉킨다.

### 브레이크포인트 없이 되는 것부터 한다

미디어 쿼리는 마지막 수단이다. 대부분은 아래로 해결된다.

```css
/* 열 수를 자동으로 — 카드 최소 폭만 정하면 알아서 늘고 준다 */
grid-template-columns: repeat(auto-fill, minmax(280px, 1fr));

/* 유동 타이포 — 단계별 점프 없이 매끄럽게 */
font-size: clamp(1.5rem, 1.1rem + 2vw, 2.25rem);

/* 본문 줄길이 제한 — 큰 화면에서 한 줄이 120자가 되는 것을 막는다 */
max-width: 68ch;

/* 여백도 유동으로 */
padding-inline: clamp(1rem, 4vw, 3rem);
```

### 컨테이너 쿼리 — 컴포넌트가 스스로 판단한다

게시글 카드는 목록(3열)에도, 마이페이지(1열)에도, 사이드바에도 놓인다. **화면 폭이 아니라 자기가 놓인 자리의 폭**을 봐야 한다.

```css
.card-list { container-type: inline-size; }

@container (min-width: 380px) {
  .card { grid-template-columns: 96px 1fr; }  /* 썸네일 가로 배치 */
}
```

화면 폭으로 판단하면 "넓은 화면의 좁은 사이드바"에서 깨진다.

### 터치와 마우스를 구분한다

```css
@media (hover: hover) {
  .card:hover { border-color: var(--ink-300); }
}
```

이 가드가 없으면 터치 기기에서 **hover 스타일이 탭 후에 들러붙는다.** 다른 곳을 누를 때까지 안 풀린다.

- 터치 대상 44×44 (마우스는 32로 줄여도 된다)
- 터치 기기에서는 hover로만 나타나는 정보를 두지 않는다. 수정·삭제 버튼을 hover로 감추면 모바일에서 영영 못 찾는다

### 높이도 반응형이다

- 가로 모드 휴대폰은 높이가 375px 남짓이다. `height: 100vh` 모달은 내용이 잘린다. `max-height: 90dvh` + 내부 스크롤
- `vh` 대신 **`dvh`** — 모바일 브라우저 주소창이 접히면 `vh`가 어긋난다
- 하단 고정 바는 `padding-bottom: env(safe-area-inset-bottom)`

### 큰 화면에서 여백만 늘리지 않는다

1440px에서 콘텐츠가 가운데 720px만 차지하고 양옆이 텅 비면 성의 없어 보인다. **정보 밀도를 올린다** — 열을 늘리거나, 필터를 접지 않고 펼치거나, 목록과 상세를 2단으로.

### 확인해야 할 폭

```
320   가장 좁은 기기 (갤럭시 폴드 접힘)
375   기준
414   큰 휴대폰
768   태블릿 세로
1024  태블릿 가로 · 작은 노트북
1440  데스크톱
```

**320px에서 가로 스크롤이 없어야 한다.** 375만 보면 폴드에서 깨진다. 브라우저 확대 200%도 같이 본다 — 저시력 사용자의 실제 환경이고, 폭이 절반이 되는 것과 같다.

## 12. 디자인은 완료되지 않는다

**"동작한다"에서 멈추지 않는다.** 화면을 만든 뒤 반드시 다시 본다.

### 만든 직후 하는 것

1. **실제로 렌더링해서 본다.** 코드만 읽고 판단하지 않는다. 375 / 768 / 1440에서 각각
2. 0장 체크리스트를 처음부터 끝까지 짚는다
3. **스크린샷을 찍어서 본다.** 화면에서 볼 때와 이미지로 볼 때 눈에 띄는 게 다르다
4. `front-review` 에이전트로 검수한다

### 한 번 더 묻는다

- 이 화면에서 **뺄 수 있는 요소**가 있나? 더할 것보다 뺄 것을 먼저 찾는다
- 처음 보는 사람이 **3초 안에** 뭘 하는 화면인지 아나?
- 이 배치 말고 더 나은 배치가 있나? 첫 안을 그대로 쓰지 않는다
- 흑백으로 바꿔도 위계가 유지되나?
- 내용이 **2배로 길어져도** 안 깨지나? 제목 100자, 댓글 300자가 실제 상한이다
- 내용이 **비어 있어도** 멀쩡한가?

### 개선은 커밋으로 남긴다

디자인 개선도 기능만큼 커밋을 쪼갠다. `게시글 카드 정보 위계 조정` 처럼 **무엇을 왜 바꿨는지** 남으면, 나중에 되돌아갈 때 근거가 된다.
